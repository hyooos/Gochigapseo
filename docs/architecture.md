# 구조와 규격

> 이 문서에 나오는 `tests/…` 파일은 GitHub 저장소 기준이다. 제출 zip에는 골든 질문셋(`tests/golden/`)만 들어 있다.

## 1. 실행 흐름
```
화면 입력 폼(이동 방법·필요 시설·한 번에 탈 수 있는 시간·출발지·관심사·일수·달) 또는 질문(str)
 └▶ Orchestrator.plan_form() / plan()   폼 값은 그대로, 질문은 규칙 해석 (API 모드면 LLM 해석 → 규칙으로 검증·보완)
     수정 대화(jeju_agent/edits.py, 규칙만·LLM 호출 0): 직전 코스를 말로 고치기·장소 하나 물어보기. 동작은 일곱 가지로 닫아 둔다 (API 모드에서는 대화 중인 말을 LLM이 먼저 이 문장 중 하나로 바꾸고, 규칙이 다시 읽어 통과할 때만 실행)
       lighter('둘째 날 빡빡해' → 그날 1곳 줄이기) / lighter_all('모든 날 줄여줘'·'너무 빡빡해') / exclude('○○ 빼줘')
       / include('○○ 다시 넣어줘') / join('엄마도 같이 가' → 일행 +1, 이용자 이동 조건은 그대로)
       / day_count('2일차 세 곳으로' → 그날 장소 수, 하루 1~5곳) / day_swap('2일차 다른 곳으로' → 그날만 다시)  + place_q('○○ 화장실 있어?' → A5)
       원칙: 확실할 때만 고치고, 아니면 코스를 그대로 두고 되묻는다(kind=ask, 누르면 바로 실행되는 답 버튼 choices)
         - 며칠째·어느 장소가 분명하지 않을 때('할머니가 힘들어', '빼줘'), 없는 날(3일 코스의 6일차)
         - 한 문장에 동작이 둘 이상이거나 코스 고치기와 조건 바꾸기(버스·일수)가 섞였을 때
         - 장소 이름이 일부만 맞으면 실행 전에 확인 카드(edit.confirm) — 빼기·다시 넣기·장소 질문 모두
         - 낱말은 끝맺음까지 본다('빼줘·빼고', '다시 넣·넣어 줘', '살려 줘'). '살려고'·'볼 게 많아'·'버스 말고 택시로'는 수정이 아님
         동의어를 늘리지 않는다: 못 알아들은 말은 수정하지 않고 보통 질문 해석으로 가거나 되묻는다
       고친 것(뺀 장소·줄인 날·여유 속도)은 다음 수정과 조건만 바꾼 이어 묻기('다시 버스로')에도 이어진다(일수를 줄이면 없어진 날만 버림).
       코스만 다시 계산·검증하고, 바뀐 점을 근거표 C6(고치기 전·고친 뒤)로 보인다.
       장소 하나 물어보기·되묻기는 직전 코스 기억을 덮지 않는다(이어서 '2일차 빡빡해'도 됨). 확인 카드가 필요 없는 수정은 바로 실행
     └▶ Plan                     확인 카드("서귀포시 · 여행 코스 짜기 · 수동 휠체어 · 장애인 화장실 필요 · 2일 · 3월 — 맞나요?") + 실행 단계 공개
 └▶ Orchestrator.execute()
     ├▶ ExploreAgent (데이터 탐색, jeju_agent/agents/explore.py)
     │     search_catalog(config/catalog.yaml) → select(고른 이유·뺀 이유) → inspect(행 수·빈 값 비율·기준일, 값은 안 냄)
     │     → 센터 표가 필요한데 없으면 센터 조회 안내(표·기간·조건). 고른 목록을 req.params["datasets"]로 넘기고,
     │       분석 에이전트는 base.uses()로 고른 자료만 쓴다(날씨 C3·버스 C4·S4·주변정보 C5). 근거표 D1(쓴 자료)·D2(뺀 자료)
     │     (API 모드) select_datasets 도구로 날씨·버스·주변정보·사진을 켜고 끔. 울타리: 핵심 자료는 못 빼고, 반출 불가 표는 못 고름,
     │       여행 달 없으면 날씨 금지, 현황에는 사진·주변정보 금지, 장소 찾기에는 버스 금지
     ├▶ AccessAgent / CourseAgent / StatusAgent .run(AnalysisRequest, ctx) → AgentResult
     │     (API 모드) LLM 판단 루프: 도구·조건 고르기 → 규칙 울타리 검사 → 코드 계산 → 결과(집계 요약) 관찰 → … → finish
     │     (키 없음·LLM 실패·AGENT_LLM=off) 규칙 판단 _run()으로 같은 계산
     │     CourseAgent는 ctx.ask("access")로 접근성 진단을 불러 후보를 받는다 (불린 쪽은 규칙 판단)
     ├▶ 근거 충분? 아니면 → 한계·필요 데이터 안내
     └▶ 설명: 문장틀 초안 → (API 모드) LLM 다듬기 → 숫자·근거표·단정 표현 대조 통과 시 채택, 아니면 초안
        (숫자: 초안·tool 결과에 있는 것만, 0~1 비율의 % 표기 허용 / 근거표: [근거표 A1] 표시 1개 이상, 없는 번호 금지 / 거부 이유는 실행 기록에)
     └▶ 검증 에이전트 verify() (jeju_agent/verify.py) — 분석을 만든 에이전트와 따로, 최종 답·결과를 규칙으로 다시 확인
        숫자 대조 · 근거표 번호 · 출처·[가상]/[실데이터] · 단정 표현 없음 · '정보 없음 ≠ 없음' · 판정 일관성 · 코스 조건(부적합·반복·하루 장소 수·이동 상한·일수·뺀 장소·줄인 날)
        · 개인 조건 기록 안 함(trace) · 센터 자료 반출 기준(10 미만 셀) · 자료 선택(고른 자료만 썼나, 반출 불가 없음)
        답 문장 때문에 걸린 LLM 설명은 문장틀로 되돌리고 다시 검사
 └▶ OrchestratorResponse          답변 + 근거표 + 경고 + 한계 + 분석 기록 + LLM 사용량 + 검증 결과(verification)
     results = [데이터 탐색, (코스면) 코스가 부른 접근성 진단, 주 결과]. 주 결과는 results[-1]
     화면: 분석 과정 한 줄(질문 이해 → 자료 찾기 → 점검 → 분석 → 검증) → 답 → 센터 안내 → 쓴 자료(D1·D2) → 리포트 → 카드 → 코스
 └▶ 보고서(Markdown) + PNG 차트 + 장소 카드(원문 근거·전화로 물어볼 말) + 방문 전 확인 목록 + 검증 결과 + (센터 자료를 썼으면) 반출 신청 사유 초안
```

## 2. 자율 수행 범위 (기획서 "판단 및 자율 수행 범위"용)

### 하위 에이전트의 LLM 판단과 규칙 울타리 (jeju_agent/agents/base.py)
LLM은 '무엇을 어떤 조건으로 실행할지'만 고르고, 숫자는 모두 코드가 계산한다. LLM에는 집계 요약만 돌아간다(장소별 원본 값 없음).
| 에이전트 | LLM이 고르는 것 | 울타리(어기면 실행 안 함, 이유를 LLM에 돌려줌) |
|---|---|---|
| 공통 | 도구·조건·반복 여부·보고할 결과(finish) | 목록·범위 밖 값 거부, 사용자가 정한 조건(지역·일수·달·이용자 조건) 변경 불가, 기본 조건 결과를 보기 전 조건 변경 거부, 필수 도구 실행 전 finish 거부, 호출마다 이유(reason) 기록, 최대 단계 수 |
| 접근성 진단 | '주의' 장소 포함 여부, 지역 밖 10·20km 확장 | 주의 포함은 적합이 3곳 미만일 때만, 확장은 지역 안 후보(적합+주의)가 3곳 미만일 때만. **경사 기준·필요 시설은 바꾸는 도구가 없다** |
| 코스 설계 | 속도(여유·보통), 하루 실내 장소 수(0~2), 이동 시간 상한(30·45·60분), 하루 화장실 장소 수(0~1) | 수동 휠체어·고령·'자주 쉬어야 함'이면 '보통' 불가, 실내 강제는 날씨 위험(비 온 날 35%↑ 또는 강풍일 20%↑)이나 실내 선호가 있을 때만, 60분은 장소가 모자란 날이 있을 때만, 코스 짜기는 최대 2번(점검 뒤 한 번 더). **부적합 장소는 어떤 조건으로도 넣지 않음** |
| 현황 분석 | 묶는 단위(시·읍면동·분류), 강조 항목(화장실·주차·대여·경사) | 지역을 정한 질문을 시 단위로 묶기 거부 |
실패·미완료 시 규칙 판단으로 돌아가며, 실행 기록에 `llm:도구`, `guard:reject`, `llm:fallback`이 남는다.

| 판단 | 누가 | 방식 |
|---|---|---|
| 질문 의도·지역·이용자 조건·일수·달 해석 | 오케스트레이터 | 규칙 / LLM(검증 후 채택, 규칙이 찾은 조건은 지우지 않음) / 화면 폼(그대로) |
| 앞 대화에 이어 읽기 | 오케스트레이터 | 규칙(되물은 질문 기억·조건 이어받기·'N일차' 수정) → 못 읽으면 LLM 대화 해석이 '지원하는 문장' 하나로 바꾸고 **규칙이 다시 읽어 통과할 때만 실행**. 키가 없으면 버튼으로 되묻기 (아래 '대화 이어가기') |
| 어떤 에이전트를 부를지 | 오케스트레이터 | 의도 → 에이전트 1:1, 코스는 접근성 진단을 연쇄 호출 |
| 장소별 적합·주의·부적합 | 접근성 진단 | 규칙 (`config/access_rules.yaml`: 이동 방법별 경사 기준, 주의가 되는 장애물, 필요 시설 없음 확인=부적합·정보 없음=주의). 경사는 caution 기준을 넘는 기록이 2곳 이상이거나 최대 경사가 caution+4° 이상일 때만 부적합, 그 밖의 초과 1곳은 주의(`slope_block`) |
| 점수 | 접근성 진단 | 확인된 사실(경사·장애물·있는 시설·관심사)만. '정보 없음'은 점수에 섞지 않고 '정보 없음 n/m'으로 따로 표시 |
| 관심사(바다·숲길·박물관·마을) | 접근성 진단 | 점수 가산만(+15). 판정(안전 기준)은 바꾸지 않음 |
| 한 번에 이동할 수 있는 시간 | 코스 설계 | 이용자가 정한 값은 **모든 이동의 상한**(첫 이동 1.5배 허용·60분 재시도도 이 값을 넘지 않음). LLM도 넘는 값을 못 고름 |
| 출발지 | 코스 설계 | 1일차 첫 이동을 출발지(읍면동 중심·공항)에서 계산. 없으면 지역 중심 → 공항 |
| 적합이 3곳 미만 → '주의' 장소도 후보에 | 접근성 진단 | 규칙 / LLM이 선택 |
| 속도·하루 장소 수 | 코스 설계 | 규칙 (여유가 필요한 조건이면 여유) / LLM이 선택 |
| 여행 달의 비 위험이 높으면 하루 1곳 실내 | 코스 설계 | 규칙 (센터 5-02 날씨) / LLM이 0~2곳 선택 |
| 장소가 모자란 날 → 이동 상한 60분으로 다시 | 코스 설계 | 규칙 / LLM이 선택 |
| 날마다 장애인 화장실 확인 장소가 있는지, 버스 정류소 거리 | 코스 설계 | 규칙 (없으면 경고) |
| 보완 우선 지역 | 현황 분석 | 규칙 (3곳 이상, 화장실 확인 비율이 전체보다 낮거나 급경사 비율이 전체보다 높은 곳) |
| 자료 노후(5년 초과)·정보 공백 경고 | 세 에이전트 | 규칙 |
| **사람 확인 지점** | 이용자 | 질문은 실행 전 확인 카드 승인, 화면 세 단계 버튼으로 조건 직접 선택, 결과의 '조건 바꾸기', 애매한 수정 요청은 버튼으로 되물어 고르게 함, 센터 CSV는 이용자가 직접 받아 넣음 |
| 최종 답·결과 다시 확인 | 검증 에이전트 | 규칙 10가지(위 1절). 단정 표현 목록은 `access_rules.yaml`의 `verify.forbidden` |
| **하지 않는 것** | — | 안전 보장("누구나 갈 수 있다"), 실시간 혼잡·운영 여부, 예약·결제, 길 안내, 의료 조언, '정보 없음'을 '없음'으로 단정 |

## 3. 규격 (jeju_agent/contracts.py)
- `TravelerProfile`: mobility(none·wheelchair_manual·wheelchair_power·walker·senior·stroller), vision, hearing, cognition(none·intellectual = 발달·지적장애, 조사 열 rec_intellectual — 무장애여행코스에만 있음), needs(acc_toilet·acc_parking·rest_often·indoor_pref), transport(car·taxi·bus), companions, budget_won, max_ride_min(10~180분), interests(sea·forest·museum·village)
- `AnalysisRequest`: question, intent(access·course·status·report·unsupported·nearby), region, origin(읍면동 또는 제주국제공항), place_ids, profile, days, month, params
  - `nearby`(근처 식당·카페·숙소)는 새 에이전트 없이 access 에이전트가 처리한다(`orchestrator.AGENT_FOR` → `AccessAgent.nearby_search`, 규칙만·LLM 판단 없음).
    분류 낱말: `KW["nearby"]`(식당·맛집·밥·카페·편의점·숙소·호텔·펜션…). 코스 요청('2일 코스 숙소도')이 먼저이고, 출발지 표현('애월에 숙소 잡았어')은 근처 질문이 아니다.
    기준 장소: '○○ 근처'면 ○○(여러 곳이 맞으면 모두). 주변정보가 없는 관광지면 3km 안의 무장애 코스 주변으로 대신 안내하고 그 사실을 답에 쓴다.
    없으면 질문 지역의 부적합이 아닌 코스 전체에서 장애인 화장실 있는 곳 먼저·가까운 순으로 8곳. 장애인 화장실이 필요한데 '없음'으로 조사된 가게는 뺀다.
- `PlaceItem`: 장소 찾기 → 코스·화면으로 넘기는 장소 1곳. 관광지·식당·카페·숙소 공통.
  item_id(관광지 place_id, 주변 장소 "C01-N3"), name, kind(attraction·restaurant·cafe·lodging), category(원본 분류), verdict(적합·주의·부적합),
  reasons, facilities(장소 카드와 같은 모양), phone, lat·lng(주변 장소는 좌표를 붙이기 전까지 비어 있음), anchor_id·distance_km(주변 장소의 기준 장소와 거리),
  source, data_date, stale, call_script. 주변정보 분류 → kind는 `NEARBY_KIND`(음식점·카페/편의점·숙박 시설).
  주변 장소 번호 N은 `nearby.csv`에서 같은 기준 장소 행들의 순서(1부터)라, 좌표(`lat`·`lng` 열)를 붙일 때 행 순서를 바꾸지 않는다.
  주변 장소의 facilities는 장애인 화장실 하나(자료 Y·N → 있음·없음). 코스는 `ctx.ask("access")` 결과의 `payload["items"]`로 받는다.
- `Verification`: passed, checks[VerifyCheck(name, ok, detail)] — `OrchestratorResponse.verification`
- `OrchestratorResponse.progress`: 화면 '분석 과정' 체크 목록. `jeju_agent/progress.py`가 실행 기록(BaseAgent.step, 오케스트레이터 기록)을 쉬운 말 한 줄로 바꾼다. 웹 서버(`web/server.py`)가 `progress.listen()`으로 실행 중에 받아 `/api/events`로 화면에 바로 보내고, 끝나면 같은 목록을 결과 아래 '근거와 검증'의 분석 과정에 남긴다. 기록은 privacy.scrub를 거친 글이라 이용자 조건 낱말이 없다. 새 기록(action)을 만들면 `progress.friendly`에 문장을 추가한다.
- `AgentResult`: agent, status(ok/partial/insufficient/error), summary, findings, evidence(근거표), warnings, confidence, limitations, follow_ups, payload, trace, data_labels
- `payload`는 다른 에이전트·이어 묻기·화면이 쓰는 기계용 값(LLM에는 보내지 않음). 현재 키:
  - access: `verdicts`(장소별 판정·점수·좌표·이유·unknown_n·checked_n), `shown_ids`, `n_ok`, `n_caution`, `n_block`, `include_caution`, `extend_km`,
    `cards`(적합·주의 장소 카드: facilities[key·label·state·mark·evidence·needed], barriers, barrier_spots, gap, source, source_file, data_date, stale, call_script),
    `coverage`(읍면동별 n·ok·caution·block·gap), `place_q`(장소 하나 물어보기의 시설 키), `nearby_kinds`(nearby 질문에서 찾은 종류),
    `items`(PlaceItem 목록: 장소 카드의 관광지 + 주변 식당·카페·숙소(주변정보 자료를 고른 경우) — 카드 순서대로 관광지 1곳 → 그 주변 장소. 코스가 kind를 보고 식당은 점심 자리, 숙소는 하루 끝에 넣는다. `access.place_items`)
  - course: `itinerary`(day·order·place_id·name·lat·lng·verdict·leg_min·leg_src(길찾기·추정)·why(선정 근거 문장)·guide(route·parking·toilet, 없으면 '정보 없음')), `place_ids`, `pace`, `indoor_per_day`, `max_leg_min`, `short_days`, `indoor_short_days`, `rain_ratio`, `wind_ratio`, `weather_risky`, `weather`, `relaxed`, `start`, `ride_cap`, `excluded_ids`, `day_caps`, `extras`(코스에 넣은 식당·숙소: PlaceItem + day·after(몇 번째 장소 뒤)·slot(점심·숙소)·anchor_name), `cards`(코스 장소 순서)
  - status: `group_by`, `focus`, `priority_groups`, `groups`
  - 공통: `decided_by="llm"`(LLM 판단 결과일 때만)
  - `params`: `opts`(에이전트 조건), `called_by`(다른 에이전트가 부른 호출), `follow_up`, `parsed`(찾은 조건 이름만),
    `datasets`(데이터 탐색이 고른 자료), `nearby_kinds`·`anchor_name`(nearby 질문의 종류·기준 장소 이름), `edit`(이번 수정), `edits`(쌓인 수정: exclude·exclude_names·day_caps·pace), `prev_itinerary`(고치기 전 코스), `place_q`
  - 대화 기억(memory): `last_request`, `last_intent`, `last_response`, `last_place_ids`, `last_itinerary`, `edits`
  새 키를 추가하면 이 표를 고친다.
- 근거표 번호: 데이터 탐색 D1(쓴 자료)·D2(쓰지 않은 자료와 이유), 접근성 A1~A5(A4 = 읍면동별 조건 충족, A5 = 장소 하나 물어보기), 코스 C1~C6(C5 = 코스에 넣은 점심 식당·숙소, C6 = 수정 대화로 바뀐 점), 현황 S1~S4, 주변 장소 N1(고른 식당·카페·숙소)·N2(기준 장소별 고른 곳·장애인 화장실 있음·전화번호 없음 수).

## 대화 이어가기 (11/17)
실제 시연에서 '2일차만 바꿔줘볼래?'에 같은 코스가 다시 나오고, '2일차만 세곳을 가게 해줘'에 조건을 다시 묻고,
그 질문에 '없어'라고 답하면 '답할 수 없는 질문'이 됐다. 원인은 ① 되물은 질문을 기억하지 않음 ② 수정 문장이 몇 개로 고정
③ LLM 해석에 이번 한 문장만 보냄. 고친 것:
- **되물은 질문 기억** (`memory["pending"]`): 조건 되묻기에 '없어'·'휠체어 타요'로 답하면 원래 질문에 붙여 실행.
  'N일차를 어떻게 바꿀까요?'에 '세 곳으로'라고 답하면 'N일차 세 곳으로'로 읽는다. 새 질문(현황 등)이면 답으로 보지 않는다.
- **조건 이어받기**: 앞 대화에 이용자 조건이 있으면 조건 없이 물은 장소·코스 질문에 그대로 쓴다('조건 없이'라고 하면 안 함).
  확인 카드에 '앞 대화의 조건 이어받음'으로 보인다.
- **날을 고치는 수정** (`edits.py`): 'N일차 M곳으로'(늘리기 포함, 하루 1~5곳) · 'N일차 다른 곳으로'(그날 장소를 빼고 그날만 다시) ·
  'N일차 바꿔줘'(되묻기 + 버튼) · 'N일차랑 M일차 합쳐줘'(되묻기: 일수 줄여 다시 짜기). 'N일차'는 일수가 아니다(규칙·LLM 해석 모두).
- **다른 날 그대로** (`keep_days` → `course.schedule(fixed=…)`): 한 날만 고치는 수정(줄이기·장소 수·다른 곳·코스 안 장소 빼기)은
  다른 날 장소를 그대로 두고 이동 시간만 다시 잰다. 고정한 날의 이동이 이용자가 정한 상한을 넘으면 그날만 다시 짠다.
  안내문은 '바뀐 날: 1일차. 다른 날은 그대로 두었습니다.'(예전 '바뀐 날은 2일'은 2일차로 읽혀 헷갈렸음).
- **LLM이 먼저, 규칙은 검증** (`prompts/dialog.md`, API 모드, 11/17 B안): 대화 중인 말(앞 결과나 되물은 질문이 있을 때)은
  규칙보다 **LLM이 먼저** 해석한다. 조건 요약·지금 코스(장소 이름)·뺀 곳·최근 질문 4개·되물은 질문을 보내고, LLM은
  edit(정해진 고치기 문장) / question(완전한 문장 + 질문 항목, 이어서인지 follow_up) / ask(되물을 말 + 고를 문장) 중 하나로 답한다.
  규칙은 낱말을 찾지 않고 **검증**만 한다: 고치기 문장은 수정 규칙이 읽어야 하고(코스에 있는 장소·날·장소 수 범위), 질문 항목은
  `_merge`(지역 사전·숫자 범위·규칙이 찾은 조건은 지우지 않음)와 조건 이어받기(LLM이 'none'이라 해도 앞 대화의 안전 조건은 남김)를 거친다.
  통과하지 못하거나 호출이 실패하면 규칙 해석으로 돌아간다. 대화 중 해석 호출은 한 턴에 1회(맥락 없는 첫 질문만 기존 질문 해석).
  관광지 원본 값·센터 자료는 보내지 않는다. 평가: `python scripts/eval_dialog.py --api`(턴별 통과·호출·비용 → outputs/dialog_report.md).
  실행 기록에는 '앞 대화로 읽음(llm) → 수정 종류'만 남기고 이용자 말은 남기지 않는다. 화면에는 이용자 말과 '무엇으로 읽었는지'를 함께 보인다.
- 키가 없을 때: 코스를 고치려는 말(날을 말함·'바꿔·다시·별로'·같은 코스 되풀이)이면 버튼으로 되묻고, 코스와 상관없는 말은 예전처럼 답할 수 없는 질문.
  키 없는 모드의 낱말 목록은 이 상태에서 더 늘리지 않는다(새 말투는 API 모드의 LLM 해석이 맡는다).
- **코스에 이어 묻기**: 코스가 있을 때 일수·지역을 새로 말하지 않은 코스 질문('그럼 숙소랑 점심도 넣어줘')은 지금 코스를 이어받고,

## 결과 화면·보고서 읽는 순서 (11/16 가독성 개선)
결과 하나는 위에서 아래로 **요약 → 답 → 장소·동선 → 근거와 검증** 순서다. 근거는 모두 남기되 접어 둔다(신뢰성 점수는 유지, 첫 화면은 짧게).
- **요약 숫자 3칸**: 접근성 = 적합/주의/뺀 곳, 장소 하나 질문 = 시설·판정·기준일, 코스 = 일정·이동 합계·가장 긴 한 번 이동,
  현황 = 관광지 수·장애인 화장실 확인 비율·정보 공백 가장 큰 항목. 칸마다 도움말(?)에 뜻을 적는다.
- **답**: 본문 문장 → '주의·한계'는 작은 글씨 상자로 뺀다(`ui_helpers.split_answer`). 검증은 나누기 전 원래 답으로 한다.
  '[근거표 A1]' 표시는 작은 글씨. 이전 답(대화 기록)도 같은 방식.
- **센터 자료 안내**: 파란 상자 대신 한 줄 + '센터 조회 사이트에서 받는 법' 펼침.
- **장소 카드**: 사진·이름·판정 배지·시설 알약(초록 ✓ 있음 / 빨강 ✗ 없음 / 회색 ? 확인 필요, 이용자가 꼭 필요한 시설은 테두리)·장애물 한 줄만 보이고,
  원문 근거·현장 안내·사진·전화로 물어볼 말은 '자세히 보기'에. 알약은 색만으로 구별하지 않게 기호와 화면 낭독기 문구를 같이 쓴다.
  조건이 없어도 기본 시설 4가지(화장실·주차·경사로·승강기)는 보인다.
- **날짜별 동선**: 날짜 칩(색 + 이름) → 방문 번호·사진·이름·배지·알약 → 다음 장소까지 '약 n분 이동'. 가족 공유 일정표 PNG 버튼은 동선 제목 옆.
  지도에서 거의 같은 자리(약 300m 안)의 번호는 한 점에 '3,4'로 모아 쓴다(`ui_helpers.merged_numbers`).
- **근거와 검증**: 쓴 자료(탐색) · 코스의 바탕이 된 접근성 진단 · 근거표 · 검증 · 분석 명세 · 분석 기록. 되묻기처럼 분석이 없는 답에는 붙이지 않는다.
- **보고서**(.md): 모든 장소에 똑같은 전화 문의는 한 번만 쓰고 카드에는 그 장소에만 해당하는 것만, 긴 원문 인용은 앞 70자.
  근거표가 12행을 넘으면 본문에는 앞 10행과 '외 n행'만, 전체 행은 맨 끝 '부록 — 근거표 전체'에(근거 번호는 그대로라 추적 가능).
  내려받기 상자(맞춤 여행 결과 아래, 대화에서는 현황 질문·'보고서로 정리해줘' 답 아래)는 버튼(보고서 .md·일정표 PNG)을 앞에, 미리 보기·그래프는 펼침에.
- 테스트: `tests/test_readability.py`.
